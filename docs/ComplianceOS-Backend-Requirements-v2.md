## 2. Architecture Overview (carried from v1)

### 2.1 Layers

```
Next.js (Vercel)  →  Express API (Cloud Run)  →  Supabase Postgres 15
                                              →  Supabase Storage
                                              →  pg-boss worker (Cloud Run)
                                              →  LaTeX renderer (Cloud Run, xelatex)
```

Worker and LaTeX renderer may share a container or split into two. The LaTeX renderer needs texlive-xetex and Arabic fonts, so an image that carries those is warranted (section 8).

### 2.2 Tenant flow

Every request carries a JWT with `tenant_id`, `role`, and `permissions`. Middleware `tenantMiddleware` extracts the claim and calls `SELECT set_config('app.current_tenant_id', $1, true)` for the request-scoped session. Every query then runs under RLS.

### 2.3 Client-side cache role

Zustand stores currently hold authoritative state with `persist()` to `localStorage`. Post-integration, every store becomes a cache over the API. Stubbed fetch methods (`fetchAll`, `fetchById`) and `TODO: Replace with actual API call` comments mark the handover surface.

### 2.4 Three-layer API pattern

- `routes/`: Express router registration, URL patterns, middleware chain.
- `controllers/`: request parsing with Zod, response shaping, HTTP status mapping.
- `services/`: business logic, transactions, cross-entity orchestration.
- `repositories/`: Postgres access via `pg` or Supabase client, RLS reliant.

Transactional work (versioning, audit log, notification enqueue, score recalculation) happens in services. See section 13.

## 3. Multi-Tenancy Design (carried from v1)

### 3.1 Strategy

Every mutable table has `tenant_id UUID NOT NULL REFERENCES tenants(id)`. RLS is enabled on every table and enforced with `tenant_id = current_setting('app.current_tenant_id')::uuid`.

### 3.2 RLS Template — Top-Level Tables

```sql
-- Applied to every top-level data table
ALTER TABLE audits ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON audits
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

CREATE POLICY tenant_insert ON audits
  FOR INSERT
  WITH CHECK (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

Top-level tables carry `tenant_id`, `created_at`, `updated_at`, `deleted_at` (soft delete).

### 3.2.1 RLS Template — Child/Junction Tables

Child and junction tables omit `tenant_id` and inherit via parent join.

```sql
-- Example: observation_assignees inherits tenancy from observations
ALTER TABLE observation_assignees ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON observation_assignees
  USING (EXISTS (
    SELECT 1 FROM observations o
    WHERE o.id = observation_assignees.observation_id
      AND o.tenant_id = current_setting('app.current_tenant_id')::uuid
  ));

CREATE POLICY tenant_insert ON observation_assignees
  FOR INSERT
  WITH CHECK (EXISTS (
    SELECT 1 FROM observations o
    WHERE o.id = observation_assignees.observation_id
      AND o.tenant_id = current_setting('app.current_tenant_id')::uuid
  ));
```

### 3.4 Express Middleware

```ts
// src/middleware/tenantMiddleware.ts
import { verifyJwt } from '../lib/auth'
import { db } from '../lib/db'

export async function tenantMiddleware(req, res, next) {
  const token = req.headers.authorization?.replace(/^Bearer\s+/, '')
  if (!token) return res.status(401).json({ error: 'unauthenticated' })
  const claims = await verifyJwt(token)
  req.user = claims
  // Bind tenant context to the current connection
  await db.query("SELECT set_config('app.current_tenant_id', $1, true)", [claims.tenant_id])
  await db.query("SELECT set_config('app.current_user_id', $1, true)", [claims.sub])
  next()
}
```

`app.current_user_id` is new in v2. The audit log trigger path (section 11) reads it.

### 4.2.1 `framework_weights` `[v1 CORRECTION]`

Source of truth: `src/types/index.ts:1118-1123` and `src/stores/framework-config-store.ts` v6 migration.

The stored per-framework `FrameworkWeights` has four keys, not seven. v1's DDL `CHECK (audits+observations+letters+policies+circulars+risk_posture+training=100)` is wrong. v2 ships:

```sql
CREATE TABLE framework_weights (
  framework_id UUID PRIMARY KEY REFERENCES frameworks(id) ON DELETE CASCADE,
  audits       INT NOT NULL CHECK (audits       BETWEEN 0 AND 100),
  observations INT NOT NULL CHECK (observations BETWEEN 0 AND 100),
  letters      INT NOT NULL CHECK (letters      BETWEEN 0 AND 100),
  circulars    INT NOT NULL CHECK (circulars    BETWEEN 0 AND 100),
  CHECK (audits + observations + letters + circulars = 100)
);
```

Department-wide weights (`policyCurrency`, `riskPosture`, `trainingCompletion`, `auditCompletion`, `observationClosure`) live in `compliance_settings.weights JSONB` (per tenant), mirroring `src/stores/compliance-settings-store.ts` L23.

### 5.26 Version history (new in v2; binds section 11)

Every versioned entity accepts `{entity_type}` = `audit | observation | risk | policy | circular | sama_letter | correspondence | advisory | calendar_event | training_course | audit_template | policy_template | sama_letter_template`.

| Method | Path | Description | Response |
|---|---|---|---|
| GET | `/api/versions/:entity_type/:entity_id` | List all versions | `{ versions: EntityVersion[] }` |
| GET | `/api/versions/:entity_type/:entity_id/:version_number` | Fetch one version snapshot | `EntityVersion` |
| GET | `/api/versions/:entity_type/:entity_id/diff?from=N&to=M` | Compute diff between two versions | `{ fields: Record<field,{from,to}>, added: [], removed: [] }` |
| POST | `/api/versions/:entity_type/:entity_id/restore` | Create new version by restoring a prior one; body `{ from_version: N, reason?: string }` | `EntityVersion` (the new version produced) |

Implementation binds to the service layer in section 13. Restore creates a new `entity_versions` row and a correlated `audit_log` row with `action='restore'`.

```ts
export function authorize(...requiredPermissions: string[]) {
  return (req, res, next) => {
    const userPerms = new Set([...(req.user.permissions ?? []), ...(ROLE_PERMISSIONS[req.user.role] ?? [])])
    for (const p of requiredPermissions) {

    next()
  }
```

## 11. Universal Versioning and Audit Trail (new in v2)

### 11.1 Scope

Every mutable entity is versioned. The table of versioned entity types is fixed and mirrors section 5.26:

`audit`, `observation`, `risk`, `policy`, `circular`, `sama_letter`, `correspondence`, `advisory`, `calendar_event`, `training_course`, `audit_template`, `policy_template`, `sama_letter_template`, `requirement`.

User-generated records in other tables (attachments, comments, checklist items, messages, notifications) are **not** independently versioned; they are captured as nested fields inside the parent entity's snapshot. Rationale: these are append-only or tied one-to-one to their parent's lifecycle; independent versioning doubles write cost without downstream value.

### 11.2 Pattern choice: single polymorphic `entity_versions` table

Two candidates were considered:

| Pattern | Pros | Cons |
|---|---|---|
| (a) Single `entity_versions(entity_type, entity_id, version_number, snapshot JSONB, …)` | Uniform schema, single query for "all changes by user X", single retention/prune job, single API shape in section 5.26, zero schema churn when adding a new versioned entity | JSONB snapshots are opaque to FK constraints; cross-entity joins require indexing on `(entity_type, entity_id)`; snapshots may be large for circulars with many articles |
| (b) Per-entity `{entity}_versions(version_number, snapshot, …)` extending `policy_versions` / `circular_versions` | Native FK to parent, typed columns possible, existing `policy_versions` / `circular_versions` stay | 14 near-identical tables, 14 retention jobs, 14 API implementations, duplicate indexing, divergent schemas over time |

Decision: **(a) single polymorphic `entity_versions` table**.

Justification grounded in query load:
- **Read load is dominated by per-entity timeline views**: "show me history for this observation". That query is `WHERE entity_type='observation' AND entity_id=$1`, fully covered by a single btree index. Per-entity tables give no advantage here.
- **Write load is one `INSERT entity_versions` per mutation** across all entities. One table means one writable target, one `pg_stat_user_tables` row to watch, one autovacuum schedule to tune.
- **Cross-entity queries** (audit-log investigations, user activity across modules) are first-class in v2. They require `WHERE actor_user_id=$1 ORDER BY created_at DESC`, which is trivial on the single table and painful across 14 tables with `UNION ALL`.
- **Storage** is acceptable: JSONB snapshots for the largest entity (a `circular` with 30 articles and full workflow) are estimated at < 50 KB; at 1000 mutations per day per tenant that is 50 MB / tenant / day, easily within Postgres comfort. If this becomes an issue, compression via `pg_toast` is automatic.
- **Existing `policy_versions` and `circular_versions`** remain in place and retain their domain-specific semantics (CircularVersionEntry `approved` flag, `fieldChanges`, PolicyVersionEntry `changes` text). They are **not duplicated** into `entity_versions`; instead, the restore helpers in section 11.7 migrate those rows into `entity_versions` on first read (lazy migration).

### 11.5 Write path: application primary, trigger safety-net

Decision: **both**. Application code in the service layer is the primary writer. A PostgreSQL trigger is a safety net on the critical tables only.

| Writer | Used for | Why |
|---|---|---|
| Service layer | All normal mutations from the API | Only the service layer has full context: which version snapshot is canonical, which fields the user intended to change, whether this mutation should emit a notification, what trigger type to send. A trigger lacks this context. |
| Trigger (SECURITY DEFINER on critical tables) | Out-of-band mutations (psql, migrations, manual DB edits, service-role scripts) | Catches writes that bypass the API. Ensures the audit log reflects reality, not API traffic. |

The trigger writes `audit_log` only; it does **not** write `entity_versions`, because versioning requires semantic decisions (is this a substantive edit? what's the `change_summary`?) that a trigger cannot make.

```sql
-- Trigger installed on audits, observations, risks, policies, circulars, sama_letters.
-- Not on every table: only the ones regulated auditors will ask "who changed what" about.
CREATE OR REPLACE FUNCTION tg_audit_log_write() RETURNS trigger
LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_tenant UUID := current_setting('app.current_tenant_id', true)::uuid;
  v_user   UUID := current_setting('app.current_user_id', true)::uuid;
  v_action TEXT;
  v_before JSONB; v_after JSONB;
  v_fields TEXT[];
BEGIN
  IF TG_OP = 'INSERT' THEN v_action := 'insert'; v_before := NULL; v_after := to_jsonb(NEW);
  ELSIF TG_OP = 'UPDATE' THEN v_action := 'update'; v_before := to_jsonb(OLD); v_after := to_jsonb(NEW);
  ELSIF TG_OP = 'DELETE' THEN v_action := 'delete'; v_before := to_jsonb(OLD); v_after := NULL;
  END IF;

  IF v_action = 'update' THEN
    SELECT array_agg(key) INTO v_fields
    FROM jsonb_each(v_after) a
    WHERE v_before->key IS DISTINCT FROM a.value;
  END IF;

  INSERT INTO audit_log (tenant_id, entity_type, entity_id, action, actor_user_id, before_json, after_json, changed_fields)
  VALUES (v_tenant, TG_ARGV[0], COALESCE(NEW.id, OLD.id), v_action, v_user, v_before, v_after, COALESCE(v_fields, '{}'));

  RETURN COALESCE(NEW, OLD);
END;
$$;

CREATE TRIGGER audit_log_observations
  AFTER INSERT OR UPDATE OR DELETE ON observations
  FOR EACH ROW EXECUTE FUNCTION tg_audit_log_write('observation');
```

Service-layer writes for normal API traffic DO run while the trigger is enabled. To avoid double-writes, one of two options:

1. Conditional trigger: skip inserts when `current_setting('app.suppress_audit_trigger', true) = 'on'`. Service layer sets this GUC inside every transaction it manages.
2. Idempotent trigger: keyed by `(entity_type, entity_id, action, txid_current())` unique constraint; second write collides and is ignored.

v2 recommends option 1 for clarity. `[OPEN QUESTION: confirm option 1 with the contractor; either is workable and the choice is cosmetic. (blocks section 11.5)]`

```ts
  listVersions(entityType: EntityType, entityId: string, opts?: { limit?: number; before?: number }): Promise<EntityVersion[]>
  diffVersions(entityType: EntityType, entityId: string, from: number, to: number): Promise<VersionDiff>

  // Restore: creates a new version whose snapshot equals the target version's snapshot,
  // applies the snapshot to the current row, writes audit_log row with action='restore'.
  restoreVersion(params: {
    entityType: EntityType
    entityId: string
    fromVersion: number
    actorUserId: string
    reason?: string
  }): Promise<EntityVersion>
}
```

### 11.7 Existing `policy_versions` and `circular_versions` coexistence

Keep the two domain tables. They carry fields `entity_versions` does not (`CircularVersionEntry.fieldChanges`, `CircularVersionEntry.approved`, `PolicyVersionEntry.changes` free text). Writes go to both: application code appends to `policy_versions` / `circular_versions` in the same transaction that appends to `entity_versions`. Reads prefer `entity_versions` for uniform snapshots; the domain tables back the existing UI (`src/stores/policy-store.ts` versionHistory list, `src/stores/circular-store.ts` versions/pendingEdit).

`[OPEN QUESTION: retention policy for `entity_versions` and `audit_log`. SAMA rules require 10 years for some artefacts; should that be the default for all, or tiered per entity? (blocks section 7 `version.prune` and section 11.3)]`

### 11.8 Restore semantics

`restoreVersion` does NOT rewind the version log. It:

1. Reads the target version's snapshot.
2. In one transaction, applies the snapshot to the current row of the parent table, appends a new `entity_versions` row with `change_type='restore'`, `restored_from=fromVersion`, and the restored snapshot.
3. Writes one `audit_log` row with `action='restore'` capturing the state before and after.
4. Emits a `entity.restored` event which feeds `notification.generate` (section 12).

This is the same pattern used in GitHub's `git revert`: history is preserved; the restore is a new commit on top.

### 12.5 `notification.dispatch` job

```
1. Lock rows where dispatched_in_app = false AND (dispatched_email = false OR dispatched_slack = false)
   FOR UPDATE SKIP LOCKED, limit 500.
2. For each row, fetch notification_preferences row for (user_id, trigger_type).
   Fall back to DEFAULT_PREFERENCES table if missing.
3. If in_app AND NOT dispatched_in_app: mark dispatched_in_app = true.
   (In-app is a no-op dispatch: the row itself is the notification; the client reads via GET /api/notifications.)
4. If email AND NOT digest_only AND NOT dispatched_email:
   enqueue `notification.email.send` job; mark dispatched_email = true.
5. If email AND digest_only AND NOT dispatched_email:
   set digest_bucket = date_trunc('day', now()) + interval '08:00';
   (digest job picks it up).
6. If slack AND NOT dispatched_slack: enqueue `notification.slack.send`; mark true.
```

Idempotency: the unique `(tenant_id, user_id, dedupe_key)` constraint prevents duplicate rows; the `dispatched_*` flags prevent duplicate sends.

### 12.6 `notification.digest.batch` job

```
1. Select notifications where digest_bucket <= now() AND dispatched_email = false
   GROUP BY user_id.
2. For each user, render one email with all grouped items (using user's locale from user_preferences.language).
3. Enqueue one `notification.email.send` per user.
4. UPDATE ... SET dispatched_email = true.
```

### 12.7 Messaging dispatch

In-app messaging is not a notification channel. It is the `message_threads` / `messages` tables in group 4.13 with its own API (sections 5.16 and 5.29). When a new message is posted, the service layer emits a `message.new` notification (trigger type) for every thread participant except the sender. That notification flows through section 12.5 normally.

## 13. Transactional Integration Pattern (new in v2)

End-to-end walkthrough: an observation is updated by a user. The service layer must, in one Postgres transaction:

1. Update the `observations` row.
2. Append an `entity_versions` row with the new snapshot.
3. Append an `audit_log` row with `action='update'`, before/after JSON, changed fields.
4. Enqueue pg-boss notification jobs respecting per-user preferences.
5. Fire a `compliance.score.recalculate` job for the affected tenant and framework.

pg-boss writes jobs into `pgboss.job`, which lives in the same Postgres instance. By calling `boss.send(...)` inside the transaction (it uses the same `pg` connection with a given schema), the enqueue is transactional: if the outer `UPDATE` rolls back, the job never becomes visible to workers. This is the outbox pattern without a separate outbox table.

### 13.1 Service method

```ts
// services/observationService.ts
import { withTx, type Transaction } from '../lib/db'
import { versioningService } from './versioningService'
import { auditLogService } from './auditLogService'
import { notificationService } from './notificationService'
import { boss } from '../lib/pgboss'

interface UpdateObservationInput {
  id: string
  patch: Partial<Observation>
  actorUserId: string
  requestId: string
  ipAddress?: string
  userAgent?: string
}

export async function updateObservation(input: UpdateObservationInput): Promise<Observation> {
  return withTx(async (tx: Transaction) => {
    // Suppress the audit trigger; service layer writes authoritative audit_log row.
    await tx.query("SELECT set_config('app.suppress_audit_trigger', 'on', true)")

    // 1. Load current state (for before_json and version snapshot diff).
    const before = await tx.one<Observation>(
      'SELECT * FROM observations WHERE id = $1 FOR UPDATE',
      [input.id]
    )
    if (!before) throw new NotFoundError('observation', input.id)

    // Ownership enforcement (section 9.5).
    await assertCanEditObservation(tx, input.actorUserId, before)

    // 2. Apply the patch and persist.
    const after = { ...before, ...input.patch, updated_at: new Date() }
    const changedFields = diffKeys(before, after)
    if (changedFields.length === 0) return before // No-op; no version, no audit.

    await tx.query(
      `UPDATE observations
         SET title = $2, description = $3, status = $4, severity = $5,
             due_date = $6, department = $7, updated_at = now()
       WHERE id = $1`,
      [after.id, after.title, after.description, after.status,
       after.severity, after.due_date, after.department]
    )
    // Child tables (assignees, checklist, updates, timeline) updated here if in patch.
    await applyObservationChildren(tx, input.id, input.patch)

    // 3. Append entity_versions row.
    const newVersion = await versioningService.appendVersion(tx, {
      entityType: 'observation',
      entityId: input.id,
      snapshot: await loadFullSnapshot(tx, 'observation', input.id),
      changeType: 'update',
      changeSummary: summarizeChanges(changedFields, before, after),
      actorUserId: input.actorUserId,
    })

    // 4. Append audit_log row.
    await auditLogService.write(tx, {
      entityType: 'observation',
      entityId: input.id,
      action: 'update',
      actorUserId: input.actorUserId,
      beforeJson: redactSecrets(before),
      afterJson: redactSecrets(after),
      changedFields,
      requestId: input.requestId,
      ipAddress: input.ipAddress,
      userAgent: input.userAgent,
    })

    // 5. Enqueue notifications. These pg-boss sends are transactional with
    //    the outer tx because we pass the same connection via the `db` option.
    await notificationService.enqueueFromMutation(tx, {
      entityType: 'observation',
      entityId: input.id,
      before,
      after,
      changedFields,
      actorUserId: input.actorUserId,
    })

    // 6. Enqueue score recalculation. One job per (tenant, framework) affected.
    for (const frameworkId of after.framework_ids ?? []) {
      await boss.send(
        'compliance.score.recalculate',
        { tenantId: before.tenant_id, frameworkId, reason: 'observation.update', entityId: input.id, versionId: newVersion.id },
        { singletonKey: `score-${before.tenant_id}-${frameworkId}`, singletonHours: 1, db: tx.rawClient }
      )
    }
    // Also the overall score.
    await boss.send(
      'compliance.score.recalculate',
      { tenantId: before.tenant_id, frameworkId: 'overall', reason: 'observation.update', entityId: input.id },
      { singletonKey: `score-${before.tenant_id}-overall`, singletonHours: 1, db: tx.rawClient }
    )

    return after
  })
}
```

### 13.2 Boundary notes

- `withTx` opens a transaction on a dedicated connection; `set_config(..., true)` binds tenant and user context for the life of the tx.
- `FOR UPDATE` on the `SELECT` prevents lost updates if two writers collide.
- `boss.send(..., { db: tx.rawClient })` uses the service-side `pg` client that pg-boss v9+ supports to enlist the job insert in the same transaction. Jobs become visible to workers only on commit.
- If any step throws, the entire transaction rolls back: the observation is unchanged, no version row, no audit row, no notification, no score recalc.
- `singletonKey` on the score job debounces: many back-to-back observation edits coalesce into one recalc.
- `redactSecrets` strips fields like user phone numbers, signature data URLs, and large binary fields from `before`/`after` JSON to keep the audit log bounded. `[OPEN QUESTION: finalize the redaction field list per entity. (blocks section 13)]`

### 13.3 Apply across every mutable entity

The same five-step shape applies to every entity. For each, define:

| Entity | Score-affecting? | Notification triggers fired | Child tables to snapshot |
|---|---|---|---|
| `audit` | yes | `audit.status_change`, `entity.assignment` | team, documents, comments, tasks |
| `observation` | yes | `observation.status_change`, `entity.assignment`, `observation.remediation_*` | assignees, checklist, updates, timeline, remediation, closure |
| `risk` | yes | `risk.status_change`, `risk.review_*` | mitigation checklist, history |
| `policy` | yes | `policy.*` | versions, workflow steps, activity, attachments, evidence, cycles |
| `circular` | yes | `circular.*`, `approval.request` on `pendingEdit` | articles, workflow, timeline, versions, pending edits, CAP |
| `sama_letter` | no | `sama_letter.*`, `approval.request`, `entity.assignment` | approval steps, timeline, attachments, observations linkage |
| `correspondence` | no | `entity.assignment` | attachments |
| `advisory` | no | `entity.assignment`, `entity.mention` on notes | notes |
| `calendar_event` | no | attendee changes → `entity.assignment` | none |
| `training_course` | yes | `training.*` | employees via progress |
| `audit_template`, `policy_template`, `sama_letter_template` | no | none | none |

## 15. Frontend Integration Risks (new in v2)

Places where frontend mock behavior will diverge from real backend behavior, and the rollback story for each.

### 15.1 Synchronous-feeling mutations become async

Every store method today returns synchronously (after an optional cosmetic `setTimeout`). Examples: `useObservationStore.create`, `usePolicyStore.approve`, `useSAMALetterStore.approveStep`. After integration these become awaited HTTP calls with real latency (50-500 ms). Risks:

- UI that reads state back immediately after a call (inside the same handler) will see stale state.
- React Query or SWR should replace `fetchAll` stubs; the existing `isLoading` booleans are insufficient for per-mutation pending states.
- Order-of-operations assumptions (e.g., create observation then add checklist items in a tight loop) must become sequential `await`s or server-side batch APIs.

### 15.2 Optimistic updates without rollback

Stores currently apply mutations optimistically. There is no rollback on failure because there is no failure mode. After integration, a 409 / 403 / 500 response leaves the UI out of sync. Required work:

- Every mutation must capture the pre-mutation state, optimistically apply, and revert on rejection.
- Form-level error surface must handle both validation errors (4xx with field details) and transport errors (network down).
- Examples most exposed: `observation-store.update` (with timeline append), `circular-store.approveCircularEditStep` (applies pending edit on all-approved), `policy-store.approve` (completes all non-complete steps).

### 15.3 Client-side pagination must become server-side

Stores that paginate in memory today (`audit-store`, `observation-store`, `risk-store`, `policy-store`, `circular-store`, `advisory-store`, `team-store`) will not scale. List screens will need `page`, `pageSize`, `sort`, `filters` parameters on `GET` endpoints and server-side result envelopes (`{ rows, total, page, pageSize }`). This is already reflected in v1 5.x endpoints; the risk is that the store reducers currently apply `filters` / `sort` / `page` after fetching the whole dataset.

### 15.4 Zustand stores assume instant consistency across tabs

`persist()` writes to `localStorage`, which is not synced across tabs or devices. After integration, a mutation in tab A is invisible to tab B until a re-fetch or push. Required:

- WebSocket or Server-Sent Events for push-driven invalidation on entities a user is viewing. `[OPEN QUESTION: should v2 include a realtime layer (Supabase Realtime / ws) or defer? The client uses localStorage persistence today; multi-device use will surface the inconsistency fast.]`
- Stores must shift from source-of-truth to cache: every mutation returns the authoritative server row; the store overwrites local state with the response.

### 15.5 localStorage persistence patterns that break with multi-device

Persisted stores today include full seed data and user-generated data in `localStorage`:

| Store | Persist key | Behavior that breaks |
|---|---|---|
| `audit-store.ts` | `audit-storage` v1 | two devices keep divergent audit lists until re-login |
| `auth-store.ts` | `auth-storage` v3 | hardcoded dev admin user; v2 migration should strip this in prod |
| `circular-store.ts` | `circular-storage` v8 | seed circulars replayed on migration; production must not seed |
| `framework-config-store.ts` | `framework-config-storage` v6 | per-tenant defaults must come from server, not ship in the bundle |
| `audit-template-store.ts`, `policy-template-store.ts`, `department-store.ts` | various | seed templates/depts must migrate to per-tenant DB rows |
| `training-store.ts` | `training-storage` v4 | v4 migration installs seed employees/courses into a real tenant |
| `user-preferences-store.ts` | `user-preferences-storage` v2 | preferences are per-user per-device today; must sync via API |
| `notification-store.ts` | `notification-storage` v3 | `read` state is device-local; users will mark-read on phone and see unread on desktop |

Mitigation:

- Build-time flag `NEXT_PUBLIC_USE_API=true` gates seed data out of production bundles.
- On first authenticated request, the client clears persisted tables that are now server-authoritative and refetches.
- Preferences and read-state specifically become pull-through: local state is best-effort cache with a push invalidation on sign-in.

### 15.6 Dedupe key drift

`src/hooks/useNotificationEngine.ts:34` builds `dedupeKey = \`${sourceType}-${entityId}-${reason}\``. The backend's `dedupeKey` MUST use the same string shape, or the frontend's `syncGeneratedNotifications` merge (`src/stores/notification-store.ts:67-92`) will duplicate rows and lose `read` state. v2 binds the backend dedupe key format to that exact shape; see section 12.3.

### 15.7 Compliance engine drift

The frontend runs the full engine in `src/hooks/useComplianceScore.ts`. If the backend engine diverges by a fractional point on any component, every dashboard in the app shows the drift. Required:

- A shared golden-test fixture: JSON `ComplianceEngineInput` → expected `ComplianceScoreResult`. Run in CI on both sides.
- `[OPEN QUESTION: who owns the golden tests, and where do they live? Proposal: `tests/compliance-engine/fixtures/` in this repo, imported by both runtimes.]`

### 15.8 Circular pending-edit approval

`src/stores/circular-store.ts:830-938` implements a pending-edit approval chain where the edit data is held in `pendingEdit` until every `approvals[]` entry is `approved`. The backend must reproduce this two-stage persistence (queue + apply). If the API naively PATCHes the circular, approvals lose their semantics.

### 15.9 Bilingual timeline text duplication

`PolicyActivityEntry` (`src/types/index.ts:663-672`) stores `textEn` and `textAr` as separate strings. The backend must render both at write time (or make the rendering synchronous during dispatch) to avoid the UI showing "en only" entries for Arabic users. `src/stores/policy-store.ts` sets both today.

### 15.10 Attachment data URLs

Several entity types (`PolicyAttachment`, `Attachment`, `LetterTemplate.defaultSignatureImageUrl`) embed base64 `dataUrl` for file content (`src/types/index.ts:643-661`, `:398`). After integration, these become Supabase Storage URLs. The frontend code downloading via `dataUrl` will need to fetch signed URLs, which changes network topology (CORS, auth header handling). Coordinate the cutover per entity to avoid mixed states.
